# 개인 포털 전환

## 작업 범위

`feat/personal-portal` 브랜치에서 기존 PHP·MariaDB 기반을 확장한다. 포털 링크는 기존 게시글과 별도의 `portal_links` 테이블에 저장한다. 관리자 한 명이 운영하는 모델이며 다중 사용자·회원 가입 기능은 포함하지 않는다.

## 화면과 데이터

- 분야: AI(`ai`), 웹개발(`web`), 파이썬(`python`), 자동화(`automation`), 기타(`other`).
- 유형: 사이트·도구(`site`), 읽을거리(`article`), 내 작업 공간(`workspace`).
- 공개 범위: 비공개(`private`) 기본값, 선택한 자료만 공개(`public`). 작업 공간은 공개를 선택해도 API에서 비공개로 저장한다.
- 태그: 최대 12개, 태그당 30자. 제목·메모·태그 검색과 태그 정확히 일치하는 필터를 지원한다.
- 상태: 고정 여부와 읽음 여부는 서로 독립적으로 변경한다. 읽음 여부는 공개 조회에서 제외한다.
- 정렬: 즐겨찾기 먼저, 순서 숫자 오름차순, ID 내림차순. 30개씩 조회한다.
- 외부 링크는 http/https만 허용하고 URL 안의 사용자명·비밀번호를 거부한다. 메타데이터를 얻기 위해 서버에서 임의 URL을 가져오는 기능은 없다.

API는 로그인 여부를 서버에서 확인한다. 프론트엔드 버튼 숨김에 의존하지 않는다. 모든 변경 요청은 POST와 CSRF 토큰이 필요하며, 로그인은 저장된 해시에 `password_verify()`만 적용한다. 동일 IP에서 15분 내 5회 시도 후 차단하고, 성공하면 해당 IP의 시도 기록을 지운다. HTTPS에서는 Secure 세션 쿠키를 사용한다.

## 기존 기록과 업로드

게시글·미디어 테이블은 그대로 유지한다. 업로드는 확장자와 실제 MIME를 검사하고 JPG/PNG/GIF/MP4/PDF만 허용한다. 새 업로드가 포함된 수정이 실패하면 DB를 롤백하고 새 파일을 정리한다. 기존 첨부파일은 DB 변경이 성공한 뒤 삭제한다. 파일 삭제 자체가 실패한 경우 서버 로그에 남으며 별도 정리가 필요하다. DB와 파일 시스템을 하나의 원자적 트랜잭션으로 묶는 것은 아니다.

기존 글쓰기·삭제·로그아웃도 새 CSRF 규칙을 적용한다. 서버에서 빠진 게시글 조회와 목록 오류 상태를 화면에 안내하며, 수정 폼 조회는 조회수를 증가시키지 않는다.

## 운영 배포 순서

1. DB 덤프와 웹 루트·업로드 폴더 백업을 확보한다. 기존 관리자 데이터의 비밀번호가 해시인지 점검한다.
2. 유지보수 시간에 `migrate-portal.sql`을 실행한다. 필요 시 기존 카테고리 이전 SQL도 적용한다.
3. DB 연결 파일을 보존하며 새 코드와 숨김 `.htaccess` 파일을 배포한다. 기존 `hash_gen.php`는 삭제한다.
4. PHP CLI 도구로 관리자 비밀번호를 교체하고 HTTPS에서 로그인한다. 서버의 PHP 확장(PDO MySQL, fileinfo), 업로드 제한, 로그 위치를 확인한다.
5. 공개·비공개 자료 저장과 로그아웃 후 비공개 접근 차단을 점검한다. `/api/config/db.php`, `/sql/schema.sql`, `/AGENT.md` 직접 접근이 403 또는 404인지 확인한다.
6. 기존 게시글 조회·작성·수정·첨부·삭제를 점검한다. FTP 교체 후에는 브라우저의 오래된 JS 캐시를 새로고침한다.

운영 서버에 아직 배포하거나 실제 DB·비밀번호를 변경하지 않았다. 현재 검증은 격리된 Apache/PHP 8.2·MariaDB 10.11 환경에서 진행한다.

## 되돌리기

- 메인 페이지뿐 아니라 인증·JS·API를 **같은 백업 버전**으로 함께 복원한다. 새 코드 일부만 남으면 CSRF·로그아웃 방식이 맞지 않는다.
- 추가한 두 테이블은 기존 코드가 참조하지 않으므로 남겨도 된다. 포털 자료가 저장되어 있으면 제거하지 않는다.
- `schema.sql`을 기존 운영 DB에 다시 실행하거나 초기 관리자 데이터를 넣지 않는다.
- 비밀번호 교체는 되돌리지 않는다. 예전 인증 코드의 평문 비교 취약점을 다시 활성화하는 버전 복원은 임시 조치로만 사용하고 보안 패치를 유지한다.
- 배포 후 발생한 새 글·첨부가 있다면 오래된 DB/업로드 백업을 무조건 덮어쓰지 않는다.

## 2차: 관심 소식

RSS 출처 관리, 마지막 수집 시각, 제목·출처·발행일·원문 링크, 중복 제거, 소식에서 보관함으로 저장을 추가한다. 페이지 접속마다 외부 피드를 모두 가져오지 않고 DB 캐시를 표시한다.

Cafe24 공유 웹호스팅은 내부 Cron 지원을 전제하지 않는다. 첫 수집은 관리자 버튼으로 실행하고, 외부 HTTP 예약 호출로 자동화를 확장한다. 외부 요청 기능을 추가할 때는 cURL·HTTPS 연결을 확인하고, 허용 출처·요청 시간·응답 크기·내부 주소 접근 제한을 별도로 구현한다. AI 요약과 번역은 수집 기능 사용성을 확인한 뒤 결정한다.
